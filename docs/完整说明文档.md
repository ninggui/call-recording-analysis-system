# 📞 通话录音批量处理系统 - 完整说明文档

版本：v2.2

## 📋 一、技能初衷

本技能的初衷是解决大量通话录音的批量转写、整理和分析问题。用户有 8000+ 个通话录音，需要：

1. 批量转写为文字内容
2. 按联系人分组合并，方便查看和检索
3. 基于 AI 摘要做深度分析，包括人物画像、沟通风格、意图与风险、自我复盘建议
4. 永久保存到飞书云文档，方便分享和协作
5. 建立多维表格知识沉淀，形成可复用的方法论

通过自动化流水线，将原本需要人工逐个处理的工作，转化为可批量、可监控、可复用的标准化流程。

## 🚀 二、使用方法

### 2.1 环境准备

- Python 3.8+
- lark-cli（飞书命令行工具）
- 飞书企业账号（需开通妙记会员额度）
- 转写额度：只在「创建妙记」时消耗，后续导出/合并/生成文档均不消耗额度

### 2.2 快速开始

1. **上传录音文件**：将所有通话录音上传到飞书云空间「通话录音」文件夹
2. **阶段1盘点**：运行 `python3 stage1_inventory.py`，盘点所有录音文件
3. **阶段2批量创建妙记**：运行 `python3 stage2_batch_pipeline.py`，批量转写录音
4. **阶段4导出**：等待转写完成后，运行 `python3 stage4_export_docs.py`，导出转写内容
5. **阶段5~8合并**：运行 `python3 stage5_8_merge_docs.py`，按联系人分组合并文档
6. **批量上传飞书**：运行 `python3 batch_upload_docs.py`，将合并文档上传到飞书
7. **深度分析**：运行 `python3 deep_analysis_v2.py`（第一层）和 `python3 deep_analysis_layer2.py`（第二层）

### 2.3 关键参数

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| 并发数 | 5 | 10 会触发限流 |
| 创建间隔 | 1.5-4 秒 | 随机间隔，避免触发限流 |
| 批次大小 | 50 个 | 每批处理 50 个文件 |
| 批次休息 | 30 秒 | 批次之间休息，避免触发限流 |
| 连续失败退避 | 5 分钟 | 连续失败后等待 5 分钟再重试 |

## ⚠️ 三、使用过程中应该注意的规则

### 3.1 飞书 API 限制

- **files list 1500 条上限**：飞书 files list API 有 1500 条隐性上限（升序降序均返回相同 1500 个文件）。解决方案：把已处理的文件移动到另一个文件夹，剩余文件就会显示出来
- **API 限流**：并发 5 个创建妙记稳定（约 900-1200 个/小时）；并发 10 个立即触发限流
- **大文档上传超时**：大文档（>100KB）上传到飞书会服务器超时，需采用分段创建+追加方案
- **子节点数量限制**：单个块的子节点数量超过限制会报错（degrade_code=4000021），大文档需要分段追加

### 3.2 认证 token 问题

- 每次运行约 10-15 分钟后认证 token 会失效（错误码 99991668，token_invalid）
- 重新启动脚本可解决
- 建议建立定时任务监控脚本状态，自动重启停止的脚本

### 3.3 重复处理问题（重要教训）

- 批量更新前必须检查已有文档：使用 drive +search 按名称搜索，而不是只依赖 files list（1500 条上限）
- 不要轻易删除已经分析好的文档：如果仅是调一下格式或者内容排布，不要轻易去删除文档，而是在原有文档上去做一个排版，这样会节约算力
- 如果删除了不该删除的文档：可以在云文档回收站里面把它进行恢复；如果恢复不了，告诉用户手动恢复
- 进度文件要及时维护和清理：避免已完成的文档还留在失败列表中，导致重复处理

### 3.4 说话人处理

- 保留 Speaker 1/2/3 原样，不做替换
- 无法确认哪个是主叫（有可能第一个讲话的是对方，也有可能是我）
- 自我复盘基于互动模式分析，不区分说话人

### 3.5 文档格式规范

- 文档标题格式：联系人原名 - YYYY-MM-DD HH:MM
- 联系人名称用文件原名不简化；纯号码文件用手机号作为联系人名
- 去掉文档中的 "+86-" 前缀（通话记录里面统一标注的，没有什么实际意义）
- 每个通话保留：AI 摘要、关键词、待办事项、章节划分、完整对话

## ⚙️ 五、技术方案

### 5.1 核心技术突破

- **飞书 files list 1500 条上限** → 自动循环分批处理（拉取 1500 个→创建妙记→移动到「已转写」文件夹→再拉下一批，循环直到源文件夹清空）
- **API 限流** → 随机间隔、批次休息、连续失败退避
- **大文档上传超时** → 分段创建+追加方案
- **四重监控保障体系** → 任务自身用 setsid 方式启动、监控脚本、cron 定时任务、自动化流水线
- **认证 token 失效** → 定时任务自动重启

### 5.2 筛选规则

- 第一批（有文字备注）：优先处理
- 第二批（无备注但多次通话）：优先处理
- 第三批（无备注单次通话）：单独放在待确认列表，人工筛选
- 直接删除：固定电话 0 开头 / 95 开头 / 公共号码等无意义通话
- 400 开头保留：放到第二批处理

### 5.3 合并规则

- 相同人多个号码/备注的文档可合并（同名同人合并，避免碎片化）
- 同名但通话批次不同的联系人保留两份（不强制合并）

### 5.4 深度分析范围

- Top 1-30：第二层深度分析（基于完整对话的互动模式）
- Top 31-50：第一层深度分析（基于 AI 摘要）
- 其余：不做深度分析，仅整合文档

## ❓ 六、常见问题排查

### Q1: 转写额度怎么计算？

A: 转写额度只在「创建妙记」时消耗，后续导出/合并/生成文档均不消耗额度。

### Q2: 为什么 files list 只返回 1500 个文件？

A: 飞书 files list API 有 1500 条隐性上限（升序降序均返回相同 1500 个文件）。解决方案：把已处理的文件移动到另一个文件夹，剩余文件就会显示出来。

### Q3: 为什么并发 10 个会触发限流？

A: 飞书 API 有限流机制，并发 5 个创建妙记稳定（约 900-1200 个/小时）；并发 10 个立即触发限流。建议使用并发 5 个，配合随机间隔和批次休息。

### Q4: 为什么大文档上传会超时？

A: 大文档（>100KB）上传到飞书会服务器超时，需采用分段创建+追加方案。先创建一个空文档，然后分段追加内容。

### Q5: 为什么认证 token 会失效？

A: 每次运行约 10-15 分钟后认证 token 会失效（错误码 99991668，token_invalid），重新启动脚本可解决。建议建立定时任务监控脚本状态，自动重启。

### Q6: 大文档追加失败怎么办？

A: 通话次数很多的大文档，采用更稳妥的追加方式：每段内容不要太大，避免「子节点数量超过限制」错误；追加失败要有重试机制和跳过逻辑，避免整批卡死。
